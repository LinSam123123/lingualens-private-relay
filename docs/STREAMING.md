# 分批、并发与逐条显示

本轮先在 Chrome 上实现。Firefox 共享同一套代码，但没有做手动验收，也没有改 Firefox 凭据存储。

## 行为

- 默认仍是非流式。设置里的「流式逐条显示」关掉时，路径与以前相同。
- 打开后，每批用 SSE 收 JSONL。一行一个完整对象 `{"id":"原始ID","text":"译文"}`。
- 网络分片、SSE 事件、完整 JSONL 条目是三种边界。半截 JSON 不写入页面。
- 只接受本批 ID。未知 ID 不写 DOM。重复 ID 不覆盖已成功译文。
- 单条无效不会清掉已成功项。无法继续安全解析时，结束该流并保留已完成项。
- HTTP 200、连接结束或部分译文都不等于整批成功。要看终止事件和缺失项。
- 流式失败不会自动再发一次非流式请求。
- 一个流从派发到结束或中止一直占用一个并发槽。默认并发 2，范围 1–10，多个标签页共用。5–10 是高级选项。
- 超时仍是派发后 25 秒，含读响应体。
- 暂停不再派发新批次，进行中的流可以跑完。取消会中止活动流并留下已成功译文。恢复原文后，旧 generation 的迟到消息被丢弃。
- 手动重试 unknown 仍会提示可能重复计费，并且只提交未完成项。它沿用原来的 request ID，这不是幂等保证。
- Port 断开不会自动重连，也不会重发已派发请求。用户明确重试时才重新绑定当前任务。旧 Port 的迟到条目会被丢掉。

## 计时不能互相替代

| 字段 | 含义 |
| --- | --- |
| 响应头 ms | `fetch` 到响应头。不是模型首 token |
| 首个文本增量 ms | 派发到第一条译文文本增量。不是完整条目 |
| 首个完整条目 ms | 派发到第一条通过校验的 JSONL |
| 收到回写确认 ms | Background 收到页面回写确认的时间，不是页面 `textContent` 自己的时钟。迟到确认会补到同一 task、request、attempt，不会写成 0 |
| 总计 ms | 该次尝试从派发到结束。重试行不沿用上一次的时钟 |
| 任务首次回写确认 / 任务结束 | 整个任务。确认时间同样不是页面时钟 |

长 DOM 节点如果被拆成多块，要等该节点的块都到齐才回写。

## 本轮没有做的验证

- 没有调用真实中转站。
- 没有用日常 Chrome 配置。
- 没有 Firefox 手动测试，没有改签名版，没有打签名包。

真实对比需要你确认后再做：同一公开页面，先非流式并发 2，再流式并发 2，然后才是流式并发 4。不要一开始用 10。Key 由你手填。
